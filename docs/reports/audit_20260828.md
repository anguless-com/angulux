# Security, dependency and performance audit — 2026-08-28

**Scope:** the whole project, at commit `f305597`.
**Advisory data as of:** 2026-08-28. CVE and advisory facts were taken from the live audit tool
and GitHub's advisory database on that date, not from recall.
**Published:** 2026-08-29, after the Critical finding and every Warning affecting the release
path were fixed and verified.

This is an internal audit published on purpose. The project's argument is that its provenance
and its supply chain can be *checked* rather than trusted, and an audit that only ever existed
privately would be the same kind of unverifiable claim the gates in `tools/` exist to replace.
Findings are published whether or not they are flattering, which is the standard
[SECURITY.md](../../SECURITY.md) sets for provenance reports filed against us.

---

## What is not in this document, and why

unfixed when this was written, and disclosing a working description of them would hand an
attacker something the project's own users cannot yet defend against. `SECURITY.md` asks
reporters to disclose privately for exactly that reason, and it would be incoherent to apply a
weaker rule to ourselves.

| Held | Severity | Area |
|---|---|---|
| 2 findings | Warning | published package code reachable by a consuming application |

Two more were held here on 2026-08-29 and are now fixed and published in full below —
W-4 and S-4 in section 2. The count above is what remains.

Two of the four are **inherited from PrimeNG 21.1.9 and still present upstream**. `SECURITY.md`
commits to telling PrimeTek and not disclosing in a way that leaves their users exposed, so

Each will be published here, in full, once fixed — in the same file, as an update. Nothing is
being dropped, and this paragraph is the record that they exist. If you are running these

[GitHub Private Vulnerability Reporting](https://github.com/anguless-com/angulux/security/advisories/new).

Everything else the audit found is below, including the things it got wrong.

## 1. Threat model

Controls without a threat model are guesses, so this came first.

### Trust boundaries

| # | Boundary | What crosses it | Assets behind it |
|---|---|---|---|
| B1 | End-user data → library components | strings rendered into templates, passthrough objects, table cell values | a consuming application's users and their sessions |
| B2 | npm registry → CI | 789 packages, four of which execute code at install time | **the npm publishing credential (OIDC)**, the GitHub token |
| B3 | GitHub PR / issue events → workflows | PR body, title, branch, fork contents | repository write access, the release path |
| B4 | primeng.dev → the upstream watch → a GitHub issue | fetched HTML | issue content; Constitution P1 |
| B5 | An LLM client → the MCP server | tool arguments | the local corpus (read-only) |
| B6 | The migration tool → a consumer's filesystem | file writes under `--write` | the consumer's source tree |
| B7 | Published artifact → consumer | tarball + provenance attestation | the MIT provenance claim |
| B8 | Docs site → visitor | prerendered HTML/JS | site visitors |

### Assets, ranked

1. **The npm publishing credential.** Whoever holds it publishes as `@anguless/*`.
2. **The MIT provenance claim.** It is a legal asset; contamination is handled as a
   supply-chain issue.
3. **Consuming applications** — the library renders their users' data.
4. Repository write access; the docs-site deployment.

### STRIDE

| Threat | Where it landed | Verdict |
|---|---|---|
| **S**poofing — publish as this project | B2/B7. OIDC Trusted Publishing, no long-lived token, `--provenance` on every publish — but dependency install scripts ran inside that same workflow. | one real gap (C-1) |
| **T**ampering | B6: a write path could leave the tree whose cleanliness it had just proved. B7: the publish guard reads bytes back out of the tarball — strong. | one real gap (held) |
| **R**epudiation | DCO walked commit-by-commit in CI, attestation gated on PR bodies, SHA-256 manifest for archived artifacts. Strong — but one written control was never switched on. | one real gap (W-5) |
| **I**nfo disclosure | No secrets in tracked files or in `git log --all -p`. Internal paths are refused in the index by a gate, not only by `.gitignore`. | clean |
| **D**enial of service | MCP tools bounded; one unbounded directory walk, minor. | acceptable |
| **E**levation of privilege | B2 → B7 is the whole of C-1. Default workflow permissions are `read`; every job narrows explicitly. | one real gap (C-1) |

### Abuse cases, written next to the use cases

- *"I compromise one transitive build dependency."* → C-1: that became npm publish rights.
- *"I move a git tag on a third-party action."* → S-3: code execution in a `pull_request_target` job.
- *"I render user-submitted data and export it."* → held.
- *"I drive component styling from server-side config."* → held.

## 2. Findings that are fixed

Every finding below was adversarially verified before it was written down — the refutations
that were attempted are recorded with it — and every one is now closed with evidence.

### C-1 · Critical · Install scripts executed inside the job holding the publishing credential

Both publishing jobs in `release.yml` declared `id-token: write` and then ran
`pnpm install --frozen-lockfile`. pnpm 9.6 runs dependency lifecycle scripts by default, and
nothing in the repository declared a policy. Four packages in the tree execute code at install
time: `esbuild` (postinstall), and `lmdb`, `msgpackr-extract` and `@parcel/watcher` (install).

**Failure scenario.** A maintainer account for one of those four is taken over and a patch
version ships a malicious `postinstall`. A release is dispatched. Because the job holds
`id-token: write`, GitHub has already placed `ACTIONS_ID_TOKEN_REQUEST_URL` and
`ACTIONS_ID_TOKEN_REQUEST_TOKEN` in the **job** environment — readable by every step and every
child process, not only the publish step. The script requests an OIDC token for the registry
and publishes as this project, **with a provenance attestation that verifies**, because the
attestation certifies the workflow that ran and this is that workflow.

**Refutations attempted, and why they failed.**

- *"Trusted Publishing pins the workflow, so a rogue script cannot use it."* The binding is
  repository plus workflow file. A script running inside that workflow satisfies it. The
  control does not fire.
- *"The OIDC variables only appear at the publish step."* They are job-scoped.
- *"`--frozen-lockfile` means nothing new can appear."* It fixes which versions, not whether
  those versions are honest, and every bump can add a package with an install script.
- *"Only four packages, all well known."* That was the count on the day, not a property.
  Nothing measured it; the number was discovered by writing a script for this audit.

**Fixed** in `59864f0`. `package.json` declares `pnpm.onlyBuiltDependencies` naming exactly
those four, so pnpm now refuses every other install script. Support was confirmed against the
pnpm 9.6.0 binary itself rather than from documentation. A new gate,
`tools/check-install-scripts.mjs`, asserts both directions — a package that builds and is not
allowlisted, and an allowlisted name that no longer builds — and refuses to run without an
installed tree rather than reporting a clean sheet it never looked for, because
lockfileVersion 9.0 records no `requiresBuild` and the installed tree is the only place the
answer exists.

**Evidence**, on a tree reinstalled from scratch under the new policy:

| Check | Result |
|---|---|
| `rm -rf node_modules` then a frozen install | exit 0, 1m32s |
| Lockfile SHA-256 before / after | identical |
| Build scripts that ran | `esbuild`, `lmdb` — both allowlisted |
| "ignored build scripts" report | none; nothing was blocked |
| Full gate suite / unit suite / tool tests | 17/17 · 3783 · 374/374 |
| Gate mutation-tested | 3/3 — each mutation turned it red |

The change is a **no-op today**: the allowlist names exactly what already ran. What changed is
that a fifth one cannot appear without pnpm refusing it and a gate saying so.

### W-1 · Warning · The publisher itself was the one unpinned thing on the release path

Both publishing jobs ran `npm install -g npm@latest` immediately before minting a credential.
Everything else on that path is pinned exactly. Two failure shapes: a compromised npm release
executing in the publish job, or — with no compromise at all — a new npm changing the OIDC
exchange so the publish fails *after* the release has already been tagged, which this project
has had to recover from before.

**Fixed** in `3cdac5d`. Pinned to the version `latest` resolved to at the time, so behaviour is
unchanged and only the drift stops, and hoisted into the workflow-level `env:` block beside
`NODE_VERSION` so there is one number rather than two copies. The comment records the debt this
creates: nothing watches it, because Dependabot parses `uses:` and manifests, never a `run:`
line.

### W-5 · Warning · A written control that was never switched on

The comment justifying the attestation skip for bot pull requests listed three machine controls
covering such a PR. Two were real. The third — that CODEOWNERS requires a maintainer review on
`package.json` and the lockfile — was not: CODEOWNERS produces review *requests*, and requiring
one takes branch protection, which had `require_code_owner_reviews: false` and
`required_approving_review_count: 0`.

This one is worth reading for how it was nearly got wrong twice.

- A first draft also claimed `SECURITY.md` repeated the assertion. Grepping it for
  review / codeowner / maintainer-approval returns **zero** matches. Claim withdrawn.
- `git push` printing `Bypassed rule violations for refs/heads/main` looks like **ruleset**
  wording and raised the possibility that a ruleset imposed a requirement the classic API
  cannot see. The finding was put on hold rather than acted on.
- The re-check first returned `[]` from the rulesets endpoint — but **unauthenticated**, while
  `gh api user` was returning 401. That `[]` was worth nothing. Treating it as evidence would
  have repeated a mistake this project has already made once, where a list endpoint reported
  zero open alerts for months while seven existed.
- Re-read with a live token: no ruleset governs `main`, and the classic settings are as stated.
  The bypass wording is GitHub's current text for classic protection.

**Fixed** in `b641329`, by making the sentence true rather than deleting it quietly. The false
bullet is replaced with a real third control — the install-script gate added in `59864f0`
covers exactly this path — and the comment records which leg was removed and why, because the
list *is* the justification for skipping the attestation.

Deliberately **not** done: switching the setting on instead. With a single maintainer, GitHub
does not permit self-approval, so a required review would make every pull request unmergeable
without an admin override. That trade is the maintainer's to make, not a side effect of
correcting a comment.

### S-1 + S-2 · The security policy described a tree that no longer existed

`SECURITY.md` had a section explaining the open Dependabot alerts, naming four against
`webpack-dev-server` and one each against `esbuild`, `@hono/node-server` and `uuid`, and
inviting the reader to "Check it yourself" with two commands.

Measured during the audit: zero open alerts, and `webpack-dev-server`, `uuid` and
`@angular-devkit/build-angular` had **zero occurrences** in the lockfile — Angular 22 builds on
vite. Both commands printed nothing. Every sentence had been true when written; the tree moved.
An empty result from a "check it yourself" command is worse than the alerts the paragraph
existed to explain.

Underneath it was the real gap: **no `pnpm audit` ran anywhere in any of the eleven workflows**,
so nothing failed on an advisory.

**Fixed** in `6772ec0`, and deliberately not by writing a fresher snapshot — a snapshot in prose
is a claim nobody checks, and a new one only resets the clock. The section now carries the claim
that cannot drift (the published packages have exactly one third-party runtime dependency
between them, verified against the built artifact) and hands over commands that read the current
state. `pnpm audit --audit-level=high` now runs daily as a second job in the licence cron, as a
separate job rather than another step so that a vulnerable dev dependency opens a security issue
rather than a P0 labelled `licensing`. The workflow was **dispatched and watched to completion**
rather than left for its first scheduled run, because this project has been bitten by a
dispatch-only workflow that had never executed.

### S-7 · Five places still said the suite had seven gates

Surfaced by the adversarial pass, not the original audit. `CITATION.cff` (which is what Zenodo
and GitHub's "Cite this repository" read) and the attic-issue seeder (which **posts its text
into public issues**) were both publishing a stale count, along with three internal sites. None
was reachable by the twelve existing gate-count patterns, because not one of them puts the
number beside the word "gates".

**Fixed** in `6f9f60a`, with six new site patterns so it cannot recur. `CITATION.cff` was
rewritten rather than renumbered, because it enumerated precisely the original seven subjects;
it now reads "among them" so the sentence stops going stale every time a gate is added.

Worth recording: **the extended gate immediately caught a bug in one of the new patterns.** A
template with no suffix after the number matched `seven` *inside* `seventeen`, because the
alternation tries the shorter word first and nothing forced it to backtrack. The fix then wrote
a single backslash, which JavaScript reads as the backspace escape inside a string literal,
producing a regex that matched nothing — and the gate caught that too, reporting the site as
*unmatchable* rather than as green. A gate that says "I could not read this" instead of "fine"
is the difference between a control and a decoration.

### W-4 · Warning · The migration tool wrote outside the tree it had just proved clean

*Held until fixed, per the rule above. Published now that it is.*

`angulux-migrate --write` offers exactly one guarantee, and its own source states it: the
work can be thrown away. `checkWritable()` enforces that by refusing to run unless the
target is a git work tree with a clean status, so `git checkout -- .` can undo everything.
There is deliberately no flag to bypass it.

But the guarantee is about the git **index**, and the scan enumerated the **filesystem**.
Those are not the same set, and every file in the difference is one the revert cannot
reach. Three ways they diverged, all measured:

1. **A symlinked directory.** `walk()` used `statSync`, which resolves links, so the walk
   recursed into the target and rewrote files outside the project.
2. **A symlinked file.** Even with `lstat`, a link to a single `.html` file is not a
   directory, so it sailed through the recursion check and was rewritten like any other
   file — through the link, onto the target.
3. **A git-ignored file, with no symlink at all.** This is the one that reproduces on every
   platform. A project whose `.gitignore` held `vendor/` was scanned, written, and
   reverted: `vendor/v.html` kept the rewritten contents. `checkWritable()` had said the
   tree was clean, and it was — ignored files do not make a tree dirty.

**Failure scenario.** A consumer runs the tool on a clean repository, as instructed. Files
in an ignored directory, or behind a symlink into a sibling checkout, are rewritten. The
report prints paths relative to the project root, so nothing on screen says another tree
was touched, and the documented undo silently does not reach them.

**A correction the verification pass forced, worth stating.** The first draft asserted the
revert never works. On Windows with a junction it does: git traverses the junction and
tracks the target as an ordinary file, so the edit shows up in `git status` and reverts
cleanly. There the tool over-reaches without losing revertibility. The unconditional hole
is the git-ignored case.

**Fixed.** Three changes, because the three divergences are not the same bug:

- `walk()` uses `lstatSync` and skips anything that is a link, so the set it yields is
  lexically inside the project — the only set the clean-tree check says anything about.
- `apply()` is an exported function that took its path from the caller on trust. It now
  resolves the target and refuses anything outside the project root, so the guarantee does
  not depend on `scan()` being the only producer of findings.
- The write path intersects the findings with `git ls-files`. A clean tree has no untracked
  files, so "not tracked" means "ignored" means "not revertible". Files left out are
  reported, not dropped silently.

**Evidence.** Three regression tests, each mutation-tested — reverting the corresponding
fix turns exactly that test red (3/3). The package suite went 33 → 37. The symlinked-file
test capability-skips on Windows, where creating a file symlink needs a privilege the
maintainer's shell does not have; it is a **declared** skip that names the reason and runs
on CI, which is Linux. A silent skip would have been the same false green this audit found
elsewhere.

### S-4 · Suggestion · A caret-measuring helper built HTML out of whatever the user typed

*Held until fixed, per the rule above. Published now that it is.*

`getCursorOffset` in `@anguless/angulux-utils` positions an overlay by cloning the input
into an invisible element and asking the browser where the caret lands. It built that
clone by assigning `innerHTML` from the text before the caret, then attached it to
`document.body`.

**Failure scenario.** A consuming application uses it to position a mention or autocomplete
popup. A user types `<img src=x onerror=…>`. The element is attached to the document, the
image fails to load, and the handler runs. Self-inflicted where the field is the user's
own; genuine stored XSS wherever the field is prefilled from someone else's content — a
shared draft, an administrator viewing a profile.

The same line was also a plain correctness bug, which is the part worth remembering: a
literal `<` in the text began a tag rather than occupying a column, so the caret offset the
function exists to compute was wrong for exactly the input that made it dangerous.

It is exported from the package and has **no caller inside this repository** — published
surface with no internal consumer, which is why it went unnoticed.

**Fixed** by building the content from text nodes and `<br>` elements. Same signature, same
return, no behaviour change for text that was never markup.

**Evidence.** Four specs in the library's browser suite, because this is a question about
what the DOM did with a string and a type checker cannot see it. They capture the element
at the moment it is attached — the function removes it before returning, so there is no
other way to look inside — and assert no `<img>` element exists, that no handler ran, that
a literal `<` survives as text, and that line breaks still produce `<br>`. Mutation-tested:
restoring the `innerHTML` assignment turns the first spec red. Suite 3783 → 3787.

## 3. Findings fixed on 2026-08-29

These three were published as open. They are now closed, and two of them turned out to be
worse than the audit had recorded — which is the argument for fixing a Suggestion rather
than filing it.

### S-3 · Every action is now pinned by commit SHA

A third-party action ran at a mutable major-version tag inside a `pull_request_target` job.
If that tag were moved, arbitrary code would run in a job holding a token — small blast
radius (the token is scoped read-only and the job never checks out the pull request), which
is why it was a Suggestion rather than a Warning.

All **45** `uses:` lines across the eleven workflows are now pinned to a commit SHA with the
tag preserved as a trailing comment, so Dependabot keeps updating them. That covers the
GitHub-owned actions too, which OpenSSF Scorecard's `Pinned-Dependencies` check reads — and
this project publishes its Scorecard badge on purpose.

**A second defect surfaced while doing it.** `tools/dump-action-inputs.mjs` regenerates the
snapshot that `check:action-inputs` validates against. Fourteen fetches in a burst tripped a
secondary rate limit, six returned nothing — and the tool wrote the snapshot anyway and
exited 0. The noisy half of that is survivable: the gate then fails saying an action "has no
recorded schema". The silent half is not. An action that passes no `with:` block is skipped
by the gate entirely, so losing *its* entry costs coverage with nothing going red. The tool
now refuses to write a partial snapshot and says why.

### S-5 · Shell interpolation in two codemods — and the verification they never ran

Two maintainer codemods built a git command by string interpolation instead of passing an
argument vector. Git permits shell metacharacters in filenames, so a maintainer running a
codemod over a hostile branch could execute them. That was the reported finding.

**Fixing it exposed something larger.** Both scripts have a `--verify` mode whose entire
purpose is to prove a codemod produced *nothing but* the rename: it reverses every file and
diffs against `git HEAD`. The path came from `path.join`, which yields backslashes on
Windows, and git rejects `HEAD:tools\foo.ts` with exit 128 — which the code caught and
treated as "new file, skip". Every file took that branch. The loop then printed

```
  compared 0 file(s), 0 mismatched
✓ Every file reverses to its exact original => the diff is a PURE rename, nothing else.
```

and exited 0. It claimed every file reversed cleanly while having compared none. All three
links are fixed: argument vector instead of a shell string, forward slashes so git accepts
the path, and a guard that refuses to print the success line when it compared nothing.
Measured after: the two verifiers now compare **726** and **863** files instead of zero.

### S-6 · The docs site has a bundle budget, and the audit had the number wrong

No budget was configured, so nothing warned on a regression. Budgets are now set on the
showcase production build: `initial` warning **380 kB**, error **450 kB**, plus an
`anyComponentStyle` budget.

**Correction to this report.** The figure published in the first version — "an initial
payload of 556 kB raw / 146 kB gzip" — was measured by summing everything `index.html`
references, including `modulepreload` hints, from a previously built copy of the site. That
is not the basis Angular's budget uses. Angular's own initial-total accounting, which is
what the builder enforces, reports **341.41 kB raw / 67.90 kB transfer**. The thresholds
above are set against that measured value, giving about 11% headroom to the warning rather
than the ~70% a budget derived from the wrong number would have allowed — a budget that
loose is decoration.

The budget was mutation-tested: dropping the error threshold to 300 kB fails the build with
`bundle initial exceeded maximum budget. Budget 300.00 kB was not met by 41.41 kB`.

## 4. Verified and dismissed

Recorded so a future audit does not re-chase them. Each was a live candidate that died under
verification.

| Candidate | Why it is not a finding |
|---|---|
| A sanitizer bypass on menu item labels | Gated behind an explicit per-item opt-in. Raw HTML requires the consumer to ask for it — the correct design. |
| Direct DOM writes in the tooltip | Gated by an `escape` option that defaults to safe. |
| Raw HTML binding in the message component | Same pattern, and a spec asserts the escaped path. |
| A sanitizer bypass in file upload | A `blob:` URL over a file the user themselves selected. Correct and necessary. |
| Prototype pollution in the merge utilities | Both write only onto a freshly created local object. A `__proto__` key retargets that object's own prototype, never `Object.prototype`. No global pollution path. |
| The MCP server, against the OWASP LLM Top 10 | Read-only over one local JSON file. No network client anywhere in the path, no caller-controlled filesystem path, no dynamic regex over caller input, results capped and contract-validated before emission. The cleanest LLM-boundary code in the audit. |
| The upstream changelog watch | Hard-fails on any URL but one, with the refusal tested *before* the request. Fetched text reaches an issue body as data, never through a shell or an expression. |
| Workflow expression injection | Every untrusted value is routed through `env:` and quoted. No `${{ github.event.* }}` reaches a `run:` body. |
| Secrets in code or history | `git grep` over the index and `git log --all -p` across every commit: zero hits for GitHub, npm, Anthropic and AWS token shapes, and for private-key headers. |
| Competing lockfiles | One lockfile. Exact pinning enforced by `.npmrc`. |
| Findings in `attic/` | Out of scope by policy: not built, not published, unreachable by a consumer. Re-flagging it would be the noise that trains people to skim. |
| Docs-site XSS surface | No sanitizer bypass anywhere in the site. Syntax highlighting ships as colour tokens through ordinary template interpolation, specifically to avoid one. Two external hosts referenced, both as links; no CDN, no fonts, no analytics. |

## 5. What the audit found in good shape

A report that lists only problems misrepresents the system.

- **The release path is unusually well built.** OIDC Trusted Publishing with no long-lived
  token; credentials not persisted on checkout; provenance on every publish; packing and
  publishing separated for a documented reason; a guard that reads `package.json` back out of
  the tarball rather than off disk; and an explicit assertion that *no* registry credential is
  configured, because a credential the tool cannot resolve is sent rather than refused and the
  registry's rejection reads like a missing package. C-1 was the one hole in an otherwise
  careful design.
- **Workflow permissions.** Default `read`; every job narrows explicitly; `pull_request_target`
  appears twice and neither instance checks out fork code.
- **`SECURITY.md`** is better than most funded projects': a real scope table, targets honestly
  marked as targets rather than an SLA, and a section written to pre-empt the obvious objection.
  S-2 was that section going out of date — a maintenance problem, not a design one.
- **Zero vulnerabilities** across the dependency tree, one lockfile, exact pinning, and a
  Dependabot configuration that documents what it refuses and why.

## 6. Method, and its limits

Findings were produced, then attacked. Every finding above was re-derived by an independent pass
whose instruction was to refute it, and that pass changed the result more than once: it killed
a claim about `SECURITY.md` that a grep disproved, corrected several citations in the first
draft that pointed at line numbers from a concatenated dump rather than the real files, narrowed
S-1 from a Warning after establishing that Dependabot alerts still fire for ignored packages,
and found the stale counts that became S-7.

Two limits worth stating plainly:

- **An audit is not a trust verdict.** `pnpm audit` matches known advisories. It cannot see a
  newly malicious or typosquatted package, which is why C-1 was treated as the top finding even
  though no dependency is known to be compromised.
- **Severity here is triaged by reachability, not by the severity column.** A high-severity
  advisory against a package that cannot reach a consumer is not a consumer's problem; a
  medium one on the release path is.

Reproducing the dependency half needs no special access:

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm audit
npm run check
```
